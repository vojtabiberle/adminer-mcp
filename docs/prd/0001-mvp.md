# PRD-0001: MVP – agent access to a database through Adminer

- **Status:** Implemented
- **Author:** Vojtěch Biberle
- **Date:** 2026-11-25
- **Related:** ADR-0001 to ADR-0011

## Problem

The databases are reachable only through a web Adminer (currently version 6.3.1) behind a VPN. A direct connection (native driver, SSH tunnel) is not available.
An agent (Claude Code and other MCP clients) cannot work with Adminer: it is an HTML application with a login form, a CSRF token and results in HTML tables.

## Goals

- The agent can read the schema and data and run queries against a database that is reachable only through Adminer.
- The agent can change data (INSERT/UPDATE/DELETE) when the profile explicitly allows it, and the MCP server prevents the most common accidents.
- Several connections (profiles) can exist at the same time, and the agent can switch between them and between databases without a restart.
- Passwords are not in the MCP client configuration, in tool parameters, or in the log.

## Out of scope

- Connecting to the VPN. The user connects before use; the MCP server does not deal with the VPN.
- Managing database users and privileges, file import, editing through Adminer forms.
- Adminer versions other than 6.3.1 (support for other versions goes through an RFC).
- Remote (HTTP) MCP transport.

## Requirements

| ID | Requirement | Priority |
|---|---|---|
| R1 | Configuration of multiple profiles. Each has an Adminer URL, driver, server, user, password, and optionally a database and a schema | Must |
| R2 | The password is loaded from an environment variable or from the system keyring | Must |
| R3 | The database is optional in the profile. Tools accept `database` (and `schema`) as call parameters | Must |
| R4 | PostgreSQL support (driver `pgsql`) | Must |
| R5 | The architecture is ready for all Adminer drivers (MySQL/MariaDB, SQLite, MS SQL, Oracle, and plugin drivers) | Must |
| R6 | Tools: list profiles, databases, schemas and tables, describe a table, read query, EXPLAIN | Must |
| R7 | An `execute` tool for INSERT/UPDATE/DELETE, available only with `allow_write` in the profile | Must |
| R8 | `execute` rejects UPDATE/DELETE without WHERE (or with an always-true WHERE) unless the agent explicitly confirms a full-table change | Must |
| R9 | The `query` tool rejects anything that is not a read, and runs in a read-only database session (ADR-0005) | Must |
| R10 | The MCP server does not wrap queries in transactions | Must |
| R11 | Results are structured (columns, types, rows, NULL distinct from an empty string) and limited by row count and size | Must |
| R12 | Automatic login and one retry after the session expires. No repeated attempts after a failed login | Must |
| R13 | Support for HTTP Basic auth in front of Adminer | Should |
| R14 | Check the Adminer version at login and warn about an untested version | Should |
| R15 | Export a query result to a local CSV/TSV file | Could |
| R16 | CLI helper to store a password in the keyring and to verify a profile login | Should |
| R17 | The MCP server does not rewrite SQL to add `LIMIT`. Tool descriptions and results warn when a result is larger than the returned rows (ADR-0010) | Must |
| R18 | On shutdown, the MCP server logs out every active Adminer session (best effort, ADR-0011) | Must |
| R19 | DDL (`CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `GRANT`, `CALL`, `DO`, …) and SQL the classifier cannot parse run in `execute` only if the profile has both `allow_write` and `allow_ddl` (ADR-0007) | Must |

## User scenarios

1. The agent explores the structure: `list_profiles` → `list_databases(profile="prod")` → `list_tables(profile="prod", database="app")` → `describe_table(table="orders", database="app")`.
2. The agent analyzes data: `query(sql="SELECT status, count(*) FROM orders GROUP BY 1", database="app")`.
3. The agent fixes data on a test profile with `allow_write = true`: `execute(sql="UPDATE orders SET status='paid' WHERE id = 42", profile="staging")`.
4. The agent sends `DELETE FROM orders` by mistake → the MCP server returns an error with an explanation and runs nothing.
5. On a production profile without `allow_write`, the `execute` tool is not available to the agent, or the agent gets a clear error.
6. On a staging profile with `allow_write` but without `allow_ddl`, the agent tries `ALTER TABLE orders ADD COLUMN …` → the MCP server rejects it and tells the agent that the profile does not allow DDL.

## Acceptance criteria

- [ ] Integration tests against Adminer 6.3.1 and PostgreSQL in Docker pass for all tools.
- [ ] NULL, empty string, multi-line text, JSON and Unicode come back unchanged.
- [ ] A wrong password causes exactly one login attempt and a clear error.
- [ ] An expired session causes one new login and the query then completes.
- [ ] `query` rejects DML, DDL, and multiple statements where any one is not a read.
- [ ] `execute` rejects `UPDATE t SET …` and `DELETE FROM t` without WHERE and with `WHERE 1=1`.
- [ ] On a profile with `allow_write = true` and `allow_ddl = false`, `execute` runs `INSERT` but rejects `DROP TABLE`, `TRUNCATE` and `DO $$ … $$`.
- [ ] `query` with `SELECT` of a function that writes fails with a read-only error from the database.
- [ ] The password does not appear in the log or in the response of any tool.
- [ ] A `SELECT` without `LIMIT` that returns more rows than `max_rows` runs unchanged, and the result contains a warning with the total and returned row counts.
- [ ] After the stdio input closes, the Adminer session is logged out (the next request with the old cookie gets the login page).

## Open questions

None. Resolved: automatic `LIMIT` → ADR-0010, logout on shutdown → ADR-0011.

## Implementation status

Implemented on branch `feat/mvp` (2026-11-26), together with RFC-0001.

- R1–R12, R14, R16–R19: implemented and covered by unit and integration tests (Adminer 6.3.1 + PostgreSQL 17 in Docker).
- R13 (HTTP Basic auth): implemented, not tested against a real proxy.
- R15 (export to a file, Could): not implemented.
- `adminer-mcp set-password` (R16) is not covered by automated tests (needs a real keyring).
